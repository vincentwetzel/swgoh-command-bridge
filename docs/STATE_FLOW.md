# State Flow

This document describes the application's state management strategy and the boundaries between live requests, local cache state, and ViewModel state. There is no automatic sync or scheduled background scraper; live work starts from an explicit user command.

## Current State
The application currently follows a simple state management approach where each feature's state is managed by its corresponding ViewModel. Character, mod inventory, priority, threshold, and optimizer state are separated into their own ViewModels.

-   **Startup:** `MainWindowViewModel` keeps cache initialization failures in a visible retryable state so the shell and Settings screen can still open while the local database issue is addressed, then loads the cached account selector before feature data and derives an account-scoped Home summary with actionable next steps.

-   **Composition:** `ApplicationComposition` creates the shared service graph once for the desktop lifetime. On Windows x64 it also owns the managed Comlink runtime when a local endpoint needs one; on other platforms or with an externally healthy endpoint it only uses the configured service. The main window disposes the runtime, HTTP client, and default database when the window closes.

-   **Data:** Fetched from services in the `Core` layer and, for current UI screens, queried from the local EF Core/SQLite cache where needed. Ally codes are normalized before Comlink calls. Comlink profiles pass through `PlayerProfileParser`, which preserves usable records when individual fields or mod entries are malformed and returns diagnostics for skipped or duplicate records. During an explicit sync, `PlayerService` opportunistically reads the Comlink metadata endpoint to resolve display names; metadata failure is non-fatal and the roster ID fallback remains usable. `PlayerService` reports connecting, mapping, persistence, and completion phases through `PlayerSyncProgress`, which Home displays during an active sync.
-   **State:** Held in properties on the ViewModels, with `StateViewModelBase<T>` centralizing loading, empty, success, and error projections over `OperationState<T>`. `MainWindowViewModel` retains separate startup and sync lifecycles because those are shell-wide workflows. Settings normalizes the supported Dark, Light, and System theme choices and applies them immediately at startup, save, and import.
-   **UI Updates:** Handled automatically by Avalonia's data binding system whenever ViewModel properties change (via `INotifyPropertyChanged`).
-   **Persistence:** `AppDbContext` stores players, characters, mods, `swgoh.gg` recommendation JSON, and bounded per-account sync outcome history in the local SQLite cache. EF Core context, entities, repositories, and the transactional `CacheSchemaMigrator` live under `src/swgoh-command-bridge.Core/Database`; startup repairs missing required tables/columns in older compatible caches, records a supported schema version, and exposes the most recent migration result. The compatibility migrator is covered by an isolated version 0-5 upgrade matrix, partial-cache repair, malformed-migration rollback, idempotence, and unsupported-future-version tests. Player replacement and account removal use explicit transactions, preserve user priorities, remove account-owned rows together, and roll back replacement changes when a later insert fails. Player rows retain the UTC time of the last successful live sync, with nullable legacy support, while sync history retains privacy-safe completed, failed, cancelled, and interrupted attempt metadata. `AppDataPaths` gives cache, settings, diagnostics, and backup operations one case-stable `SWGOHCommandBridge` application-data directory on every platform. Settings create schema-stamped and integrity-checked SQLite backups, reject unsupported future-schema or out-of-scope files before replacement, restore through a temporary file with rollback protection, and perform confirmation-guarded reset/restore actions that preserve JSON application settings. Versioned secret-safe settings transfer is also available. `SettingsService` stores application configuration in an atomic versioned JSON envelope and migrates legacy plain settings, including stable threshold IDs and default selection.

-   **Diagnostics:** `DiagnosticsViewModel` reports cache reachability, aggregate record counts, safe configuration metadata, the latest persisted sync outcome, the ten most recent redacted sync attempts, the persisted scraper summary, and bounded in-memory application events. Its loading, success, and unavailable-cache error states are visible in the screen, with retry for cache failures; export omits full ally codes, account payloads, access keys, and session values.

## Feature State
-   **Characters:** `CharactersViewModel` loads cached characters for the active ally code, applies search text, orders by priority then name, and exposes explicit non-preview UI state.
-   **Accounts:** `MainWindowViewModel` lists cached players by ally code, persists the selected cached account as the default, can remove a selected account after confirmation along with its roster/mod rows, reports active character/mod counts on Home, and reloads all feature screens from SQLite without contacting Comlink; an empty active scope shows no account data instead of falling back to every cached account. Syncing remains an explicit user action with visible phase progress, a final character/mod/warning summary, immediate cancellation feedback, categorized failure messaging, cache-preservation messaging, and retry availability.
-   **Character Priorities:** `CharacterPrioritiesViewModel` loads cached characters for the active ally code, mirrors the selected character priority into an editable property, validates the 0–100 range, exposes dirty-state cancel behavior, and persists priority changes through `AppDbContext`.
-   **Thresholds:** `ModThresholdsViewModel` loads backward-compatible threshold settings, preserves stable IDs, supports duplicate/edit/delete flows, validates values before saving or importing, persists the selected default threshold, and exports/imports a versioned JSON threshold document.
-   **Mods:** `ModsViewModel` loads the SQLite inventory and cached character/equipped-mod context into memory, projects roster names plus readable quality, set/slot, primary, and compact secondary-stat summaries onto virtualized mod rows, applies the screen's slot, set, primary, comma-separated secondary-stat combination/value, minimum-level, tier, pips, equipped, and deterministic sort filters, reports filtered-result counts with a reset action, pages matching results in 100-item windows, shows readable selected-mod secondary stats and set/slot labels, shows the active persisted advisor threshold and current/projected secondary-roll efficiency estimate, then asks `IModAdvisorService` for the selected mod recommendation without allowing stale asynchronous results to overwrite a newer selection.
-   **Optimizer:** `ModOptimizerViewModel` loads cached characters and mods for the active ally code, reads the shared account-scoped `RecommendationSnapshot` for the selected character, identifies current versus seven-day-stale or missing community data, exposes target sets/primaries, consumes `ModLoadoutResult` for completeness, set-rule validity, status, per-mod explanations, combined assignment score, alternative/swap score deltas, and conservative current-versus-proposed persisted mod-stat deltas, and can request either a priority-first roster plan or a bounded joint roster plan that reserves each mod once, reports conflicts, and surfaces consolidated swap candidates with availability/reservation context. Score and projection comparisons are explicitly labeled as estimates rather than guaranteed in-game stat gains.
-   **Scraping:** `SwgohGgScraperService` reports `ScrapeProgress`, delegates markup handling to `SwgohGgRecommendationParser`, supports selected-character and active-ally-code-scoped all-character refreshes with cancellation, skips fresh recommendations, uses bounded identifying requests with optional configured contact metadata, applies a validated configurable retry/backoff/pacing policy with `Retry-After` support, records failures without requiring a scheduled background worker, and the optimizer persists the last refresh summary in application settings.

## Comlink startup lifecycle

1. `MainWindowViewModel.InitializeAsync` initializes or repairs the local cache, then prepares Comlink before loading cached accounts.
2. `ApplicationComposition` asks `IComlinkRuntimeManager` to check the configured endpoint. A healthy endpoint is reused.
3. On Windows x64, an unavailable local endpoint causes the manager to reuse a cached pinned binary or download a compatible release, start a hidden child process, and poll the endpoint until ready. Progress is shown in the shell.
4. A failed setup leaves cached account data available offline and records a privacy-safe event. A successful owned process is stopped when the composition is disposed.

## Operation lifecycle

User commands follow this pattern: validate input, enter a loading state, perform a cancellable Core operation, persist successful results, refresh affected ViewModels, and finish in success, empty, cancelled, or error state. Cancellation is not treated as a successful refresh. Existing valid cache data remains available when a later request fails or is cancelled.

## Future Considerations
If the application's state becomes more complex and needs to be shared across multiple, disconnected ViewModels, a more centralized state management solution might be considered, such as:

-   A singleton "Application State" service.
-   A message bus (e.g., using `CommunityToolkit.Mvvm.IMessenger`).
-   A state management library like Redux.NET.
